# 機能仕様書: web-screen-capture

**作成日**: 2026-05-20

**ステータス**: 確定

---

## 問題設定と目標

### 背景

チームがウェブページのスクリーンショットをレビューする場面（デザインレビュー、競合調査、リグレッションチェックなど）では、以下の課題がある。

1. **手作業の非効率性** — 複数URLを個別にキャプチャし、手動でフォルダ管理する作業が繰り返し発生する。
2. **コンテキストの消失** — 画像ファイルだけでは「誰が、いつ、何の目的でキャプチャしたか」が残らない。
3. **レビューフィードバックの散在** — スクリーンショットへのコメントがチャット・メール・別ドキュメントに分散し、追跡が困難。
4. **視覚的指摘の曖昧さ** — 「この部分が問題」を伝えるために画像編集ソフトを開いて注釈を手書きする必要がある。

### 解決する問題

チーム全員が使えるCLIツールを提供し、スクリーンショットのキャプチャ・整理・コメント・アノテーションをひとつのワークフローとして完結させる。スクリプトやCI/CDパイプラインに組み込める設計とし、データは開かれた形式でエクスポート可能とする。

### 目標

| 目標 | 指標 |
|------|------|
| バッチキャプチャの自動化 | 1コマンドで複数URLを処理できる |
| キャプチャの文脈保存 | URL・タイムスタンプ・ラベルをメタデータとして保持 |
| チームレビューの効率化 | コメント・スレッドを構造化データで記録・閲覧できる |
| 視覚的フィードバックの明確化 | 矩形・矢印・テキスト等のアノテーションを構造化データで保存 |
| データの可搬性確保 | JSON + 画像ファイルとしていつでもエクスポートできる |

### ストーリー 1 — バッチURLキャプチャ (優先度: P1)

チームメンバーが複数のウェブページを一括でスクリーンショット撮影したい。
CLIに複数URLを直接渡すか、URLリストファイルを指定することで、ひとつのコマンドで全ページをキャプチャし、メタデータ（URL・タイムスタンプ・ラベル）とともにローカルに保存する。
1件のキャプチャが失敗しても残りは続行し、URLごとの成否がレポートされる。

**この優先度の理由**: ツールの存在意義そのものがバッチキャプチャにある。他のすべての機能（コメント・アノテーション）はキャプチャなしには成立しない。

**独立テスト方法**: URLを2〜3件指定してコマンドを実行するだけで完結する。画像ファイルとメタデータが保存されれば価値が確認できる。

**受け入れシナリオ**:

1. **前提**: コマンドが使用可能な状態で、**操作**: 有効なURLを3件コマンドライン引数で指定してキャプチャコマンドを実行する、**結果**: 3件分のPNG画像とメタデータが保存され、各URLの成否が出力される。
2. **前提**: URLリストファイル（1行1URL）を用意した状態で、**操作**: `--url-file` オプションにそのファイルを指定する、**結果**: ファイル内の全URLが処理され、個別の成否がレポートされる。
3. **前提**: リストに到達不能なURLが1件含まれる状態で、**操作**: バッチキャプチャを実行する、**結果**: 失敗したURLは失敗としてレポートされるが、他のURLのキャプチャは完了し、全体の終了コードは非ゼロとなる。
4. **前提**: バッチキャプチャが完了した状態で、**操作**: `--json` フラグ付きで同コマンドを実行する、**結果**: URLごとの成否・保存パス・メタデータを含む有効なJSONが `stdout` に出力される。

### ストーリー 2 — キャプチャの閲覧・一覧表示 (優先度: P2)

チームメンバーが過去のキャプチャを検索・閲覧したい。
CLI経由でキャプチャの一覧を表示し、特定のキャプチャの詳細（URL・日時・ラベル・保存パス）を確認できる。

**この優先度の理由**: キャプチャ後にデータを参照できなければ、ストーリー1で保存した情報が活用されない。コメント・アノテーション機能はこの閲覧機能を前提とする。

**独立テスト方法**: キャプチャが1件以上保存された状態で `list` コマンドを実行し、一覧が表示されることを確認する。

**受け入れシナリオ**:

1. **前提**: キャプチャが複数件保存されている状態で、**操作**: `list` コマンドを実行する、**結果**: 各キャプチャのID・URL・タイムスタンプ・ラベルが人間が読める形式で一覧表示される。
2. **前提**: キャプチャが存在する状態で、**操作**: `show <capture-id>` コマンドを実行する、**結果**: 指定したキャプチャの詳細（URL・タイムスタンプ・ラベル・画像パス・コメント数・アノテーション数）が表示される。
3. **前提**: 任意の状態で、**操作**: `list --json` を実行する、**結果**: キャプチャの配列を含む有効なJSONが `stdout` に出力される。
4. **前提**: キャプチャが0件の状態で、**操作**: `list` を実行する、**結果**: 空リストを示すメッセージが出力され、終了コードは0となる。

### ストーリー 3 — テキストコメント追加 (優先度: P3)

チームメンバーが特定のキャプチャに対してコメントを投稿し、他のメンバーとスレッド形式で議論したい。
コメントには投稿者識別子とISO 8601タイムスタンプが自動的に記録され、既存コメントへの返信も可能。

**この優先度の理由**: バッチキャプチャと閲覧が機能した後、次に求められるのはチームの意見をキャプチャに紐付ける手段である。コメント機能なしでもツールとして成立するが、チームコラボレーションの核心はここにある。

**独立テスト方法**: キャプチャ1件に対してコメントを追加・閲覧・返信する操作のみで完結する。アノテーション機能は不要。

**受け入れシナリオ**:

1. **前提**: キャプチャが1件保存されている状態で、**操作**: `comment add <capture-id> --author "alice" --message "ヘッダーの配色が問題"` を実行する、**結果**: コメントが保存され、IDと作成日時が表示される。
2. **前提**: コメントが1件ある状態で、**操作**: `comment reply <comment-id> --author "bob" --message "同意します"` を実行する、**結果**: 返信が元コメントのスレッドに紐付けられて保存される。
3. **前提**: コメントとスレッドが存在する状態で、**操作**: `comment list <capture-id>` を実行する、**結果**: ルートコメントと各スレッドの返信がツリー形式（またはインデント付き）で表示される。
4. **前提**: 任意の状態で、**操作**: `comment list <capture-id> --json` を実行する、**結果**: コメントの配列（各要素に author・content・timestamp・replies フィールド含む）を含む有効なJSONが出力される。

---

### ストーリー 4 — 画像アノテーション追加・閲覧 (優先度: P4)

チームメンバーがキャプチャの特定領域に対して矩形・矢印・テキストラベル・ハイライトを追加し、視覚的なフィードバックをチームと共有したい。
アノテーションは構造化データ（座標・種類・スタイル・内容）としてキャプチャとは別に保存され、後から編集・削除が可能。

**この優先度の理由**: テキストコメントよりも実装コストが高いが、「どの箇所の問題か」を明示するためにアノテーションは重要なユースケースである。コメント機能が確立した後に追加すると価値が最大化される。

**独立テスト方法**: キャプチャ1件に対してアノテーションを追加・一覧表示・削除する操作のみで完結する。画像へのピクセル書き込みは不要。

**受け入れシナリオ**:

1. **前提**: キャプチャが1件保存されている状態で、**操作**: `annotation add <capture-id> --type rect --x 100 --y 200 --width 300 --height 150 --color red --label "修正箇所"` を実行する、**結果**: アノテーションが構造化データとして保存され、IDが表示される。
2. **前提**: アノテーションが1件存在する状態で、**操作**: `annotation list <capture-id>` を実行する、**結果**: 種類・座標・スタイル・内容を含むアノテーション一覧が表示される。
3. **前提**: アノテーションが1件存在する状態で、**操作**: `annotation delete <annotation-id>` を実行する、**結果**: アノテーションが削除され、元の画像ファイルは変更されない。
4. **前提**: アノテーションが存在する状態で、**操作**: `annotation list <capture-id> --json` を実行する、**結果**: type・coordinates・style・content・created_by・created_at を含む有効なJSONが出力される。

### ストーリー 5 — データエクスポート (優先度: P5)

チームメンバーがキャプチャ・コメント・アノテーションのすべてのデータを開かれた形式でエクスポートし、他のツールや別の環境への移行に使用したい。

**この優先度の理由**: 最低限、内部データが読み取り可能な形式で保存されればエクスポートは後回しにできる。ただしデータポータビリティは長期的な信頼の基盤となる。

**独立テスト方法**: エクスポートコマンドを実行し、生成されたJSONファイルと画像ファイルを別のディレクトリで確認するだけで完結する。

**受け入れシナリオ**:

1. **前提**: キャプチャ・コメント・アノテーションが存在する状態で、**操作**: `export --output ./my-export` を実行する、**結果**: 指定ディレクトリにJSONメタデータファイルと画像ファイルが生成される。
2. **前提**: エクスポートが完了した状態で、**操作**: エクスポート先のJSONファイルを確認する、**結果**: すべてのキャプチャ・コメント・アノテーションデータが包含され、画像パスが相対パスで記録されている。
3. **前提**: ストレージにデータが存在しない状態で、**操作**: `export` を実行する、**結果**: 空のエクスポート（空のJSONまたは空ディレクトリ）が生成され、エラーは発生しない。

---

### エッジケース

- 同じURLを同じバッチ内に重複して指定した場合、両方キャプチャされるか、重複が検出されて警告されるか？
- キャプチャ中にページのJavaScriptが無限ループした場合、タイムアウトはどう機能するか？
- アノテーションの座標が画像サイズを超えている場合、バリデーションエラーが返るか？
- 非常に大きなURLリストファイル（数千件）を指定した場合、メモリやファイルディスクリプタの問題が発生しないか？
- `--author` を指定しないでコメントを追加した場合、どうなるか（エラーか、匿名投稿か）？
- ストレージが破損または不整合な状態になった場合、リカバリ手段はあるか？

## 要件 *(必須)*

### 機能要件

#### キャプチャ

- **FR-001**: システムは1回のコマンド実行で複数のURLを受け付け、すべてのキャプチャを試みなければならない。
- **FR-002**: 個別のURLキャプチャが失敗しても、バッチ全体の処理は継続しなければならない。
- **FR-003**: 各キャプチャの成否・失敗理由は、人間が読める出力とJSON出力の両方で報告されなければならない。
- **FR-004**: キャプチャにはURL・キャプチャ日時（ISO 8601）・任意のラベル/タイトルをメタデータとして記録しなければならない。
- **FR-005**: スクリーンショットはデフォルトでPNG形式で保存されなければならない。
- **FR-006**: キャプチャにはヘッドレスブラウザ（またはブラウザ自動化エンジン）を使用し、JavaScriptが描画するページを正しく取得しなければならない。
- **FR-007**: URLリストをファイル（1行1URL）から読み込む `--url-file` オプションを提供しなければならない。
- **FR-008**: ネットワーク操作（キャプチャ）には設定可能なリトライ戦略を実装し、一時的な障害に対してデフォルトのリトライ動作を持たなければならない。

#### CLI・出力

- **FR-009**: データを返すすべてのコマンドに `--json` フラグを提供し、有効なJSONを `stdout` に出力しなければならない。
- **FR-010**: エラーメッセージは `stderr` に出力され、何が失敗し、なぜ失敗し、どう対処すべきかを明示しなければならない。
- **FR-011**: 成功時の終了コードは0、失敗時は非ゼロでなければならない。バッチ処理の部分的失敗も非ゼロとする。
- **FR-012**: すべての設定可能な値（タイムアウト・出力ディレクトリ・ストレージバックエンド・リトライ回数）は設定ファイルとCLIフラグの両方で指定でき、CLIフラグが優先されなければならない。

#### コメント

- **FR-013**: コメントはキャプチャIDに紐付けて保存され、投稿者識別子とISO 8601タイムスタンプを必ず記録しなければならない。
- **FR-014**: コメントはスレッドリプライをサポートしなければならない。返信は親コメントに紐付けられ、返信自体も投稿者識別子とタイムスタンプを持たなければならない。
- **FR-015**: コメントデータは構造化・クエリ可能な形式で保存されなければならない（非構造化テキストダンプは不可）。

#### アノテーション

- **FR-016**: アノテーションは矩形・矢印・テキストラベル・ハイライトの4種類に対応しなければならない。
- **FR-017**: アノテーションは座標・種類・スタイル・内容を含む構造化データとして、ベース画像のピクセルとは別に保存されなければならない。
- **FR-018**: 個々のアノテーションを削除できなければならず、削除後も元の画像ファイルは変更されてはならない。

#### ストレージ・エクスポート

- **FR-019**: ストレージバックエンドは明確に定義されたインターフェースの背後に抽象化され、CLIコマンドや操作を変えることなく交換可能でなければならない。
- **FR-020**: データはJSON メタデータファイル + 画像ファイルの形式でエクスポートできなければならない。エクスポートは完全かつ自己完結型でなければならない（別のストレージ参照に依存しない）。

### 主要エンティティ *(データを扱うため含む)*

- **キャプチャ (Capture)**: スクリーンショット1件を表す。識別子・URL・キャプチャ日時・ラベル/タイトル（任意）・保存された画像への参照・キャプチャ結果ステータスを持つ。
- **コメント (Comment)**: キャプチャに紐付くテキスト投稿。識別子・対象キャプチャへの参照・投稿者識別子・テキスト内容・ISO 8601タイムスタンプ・親コメントへの参照（返信の場合）を持つ。
- **アノテーション (Annotation)**: キャプチャ上の特定領域への視覚的マーキング。識別子・対象キャプチャへの参照・種類（rect/arrow/text/highlight）・座標・スタイル情報・テキスト内容（任意）・作成者識別子・作成日時を持つ。

## 成功基準 *(必須)*

### 測定可能なアウトカム

- **SC-001**: チームメンバーが10件のURLをバッチキャプチャし、全URLの成否を確認するまでの操作を3分以内に完了できる。
- **SC-002**: バッチ内の1件のキャプチャ失敗が他のキャプチャをブロックしない（失敗率100%以外のバッチでは部分的な成果物が必ず得られる）。
- **SC-003**: `--json` 出力がスクリプトや他のツールとのパイプ処理でエラーなく消費できる（有効なJSON仕様への準拠）。
- **SC-004**: 同一キャプチャに対して複数メンバーがコメントを投稿・返信した場合、元のスレッド構造が崩れることなく閲覧できる。
- **SC-005**: すべてのアノテーションデータが構造化形式で保存・取得でき、元の画像ファイルに変更が加わらない。
- **SC-006**: エクスポートしたデータセットから、外部ツールを使ってすべてのキャプチャ・コメント・アノテーションを再構築できる（ストレージバックエンドへのアクセス不要）。
- **SC-007**: すべてのCLIコマンドが、何が失敗しどう対処すべきかを明示したエラーメッセージを返す（曖昧なエラー出力が0件）。

## スコープ外

以下はこの仕様のスコープ外とし、将来のバージョンで検討する。

| 項目 | 理由 |
|------|------|
| グラフィカルUI（ウェブ・デスクトップ） | CLI-Firstの原則に従い、GUIは計画外 |
| リアルタイム同期・ライブコラボレーション | サーバー依存性が発生し、シンプルさの原則に反する |
| クラウドストレージの標準実装 | ストレージ抽象化層は設計するが、クラウド実装はv1スコープ外 |
| 動画・GIFキャプチャ | 静止画キャプチャのみ対象 |
| アクセス制御・認証・パーミッション管理 | チーム内でストレージを共有する前提; 認証は外部手段で対応 |
| アノテーションを画像に合成するエクスポート | 構造化データとしての保存を優先; 合成エクスポートは将来の拡張 |
| PDF・HTML形式でのエクスポート | JSON + 画像ファイルのみ |
| ブラウザ拡張機能 | CLIツールとして完結 |
| スクリーンショットの差分比較機能 | 将来のユースケース |
| モバイル端末でのエミュレートキャプチャ | デスクトップビューポートのみ（CLIフラグでのビューポートサイズ指定は除く）|

## 前提事項

- チームメンバーは全員、同一のファイルシステムまたはネットワーク共有にアクセスできる（共有ストレージの設定は各チームの責任）。
- ヘッドレスブラウザが実行環境にインストール・設定されているか、ツールのセットアップ手順に含まれる。
- **著者識別子の優先順位**: 設定ファイル（`.wsc/config`）→ 環境変数（`WSC_AUTHOR`）→ CLIオプション（`--author`）の順で設定できる（ログイン認証は行わない）。
- 実装言語は初回の詳細設計（plan）で決定する。一度決定したら構成上の理由がない限り変更しない。
- **ストレージバックエンド**: フラットJSONファイル（メタデータ）＋ローカルファイルシステム（PNG画像）を採用する。ポータビリティを最優先とし、シンプルな構成とする。
- **デフォルト保存先**: カレントディレクトリ配下の `.wsc/` ディレクトリ。プロジェクトごとに独立したデータ管理が可能。
- **画像フォーマット**: PNGのみサポート。JPEG・WebP対応はv1スコープ外。
- **アノテーション追加**: キャプチャ後に `annotation add <capture-id>` サブコマンドで追加する方式のみ（バッチキャプチャとの分離を維持）。
- **アノテーション合成エクスポート**: アノテーションのピクセル焼き込みはv1スコープ外。構造化データとしての保存・エクスポートのみ。
